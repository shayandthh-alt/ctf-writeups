# Functional Budget — Misc Write-up

## معرفی و تصویر کلی چالش
**«بعد از آخرین جلسه بودجه‌مون، متوجه شدیم که داریم از تعداد خیلی زیادی تابع استفاده می‌کنیم. برای اینکه سودمون در شرکت Brunnerne Inc. به حداکثر برسه، تصمیم گرفتیم از این به بعد فقط از یک تابع استفاده کنیم. برای همین، این برنامه رو ساخته‌ایم تا کارمندهایمان را برای این پارادایم جدید آموزش بدهیم.»**


چالش **Functional Budget** از آن دسته مسئله‌های Misc است که در نگاه اول خیلی ساده به نظر می‌رسد: سرویس در هر round یک معادله‌ی خطی مثل

```text
37x + 12 =
```

به ما می‌دهد و از ما می‌خواهد یک expression وارد کنیم که برای هر `x` همان مقدار `37x + 12` را تولید کند.

اما یک محدودیت عجیب وجود دارد: ما اجازه نداریم `+`، `-`، `*`، اعداد مختلف یا حتی یک ثابت دلخواه را مستقیم بنویسیم. Grammar فقط این است:

```text
E = 1 | x | eml(E, E)
```

و تنها عملگر واقعی هم این است:

```python
eml(x, y) = exp(x) - ln(y)
```

پس مسئله‌ی واقعی این نیست که «معادله را حل کنیم». باید از همین یک primitive آن‌قدر توان محاسباتی استخراج کنیم که در نهایت بتوانیم `a*x+b` را بسازیم.

نکته‌ی خیلی قشنگ چالش اینجاست: **`eml` به تنهایی خیلی عجیب به نظر می‌رسد، ولی با چند identity جبری می‌توانیم از آن `exp`، `ln`، تفریق، جمع و ضرب بسازیم.** بعد از آن، `a*x+b` دیگر مسئله‌ی خاصی نیست.

---

## ساختار خود چالش

کد challenge یک parser برای grammar بالا دارد و expression را روی 100 مقدار تصادفی `x` آزمایش می‌کند. بخش مهم آن این است:

```python
for _ in range(100):
    x = random.uniform(-10000, 10000)
    evaluated = evaluate(expr, x).real
    if abs(a*x + b - evaluated) > 1e-6:
        print("Wrong")
        exit()
```

یعنی لازم نیست expression ما دقیقاً همان شکل `a*x+b` را داشته باشد؛ فقط باید مقدار عددی آن، برای همه‌ی مقادیر ازمایشی، با `a*x+b` یکی باشد.

این نکته بعداً در بحث **اعداد مختلط** خیلی مهم می‌شود.

---

# 1. نقطه‌ی شروع: شکستن `eml`

تعریف داریم:

```text
eml(x, y) = exp(x) - ln(y)
```

اولین کاری که باید بکنیم این است که ببینیم اگر یکی از ورودی‌ها را هوشمندانه انتخاب کنیم، چه primitive ساده‌ای به دست می‌آید.دقت کنیم که در اینجا 'exp' تابع نمایی و 'ln' یا 'log' لگاریتم است.(به صورت خاصتر 'ln' لگاریتم طبیعی یا در مبنای ۱۰ هست.)

### ساختن `exp`

چون:

```text
ln(1) = 0
```

پس:

```text
eml(x, 1)
= exp(x) - ln(1)
= exp(x)
```

بنابراین:

```text
exp(x) = eml(x, 1)
```

در solver:

```python
def EML(a, b):
    return f"eml({a},{b})"


def EXPF(v):
    return EML(v, "1")
```

---

# 2. ساختن `ln`

اینجا بخش جذاب مسئله شروع می‌شود.

می‌خواهیم از `eml` خود `ln(x)` را استخراج کنیم.

اول:

```text
eml(1, x) = e - ln(x)
```

حالا این را دوباره در `eml(..., 1)` قرار می‌دهیم:

```text
eml(eml(1, x), 1)
= exp(e - ln(x))
= e^e / x
```

و دوباره:

```text
eml(1, e^e/x)
= e - ln(e^e/x)
```

در نتیجه، با استفاده از رابطه‌ی لگاریتمی، مقدار حقیقی مورد نیاز برای solver به `ln(x)` برمی‌گردد.

پس از نظر ساختار:

```text
ln(x) = eml(1, eml(eml(1, x), 1))
```

و دقیقاً همین expression در solver ساخته شده است:

```python
def LOG(v):
    return EML("1", EML(EML("1", v), "1"))
```

### یک نکته‌ی مهم درباره‌ی اعداد منفی

چالش با `numpy.complex128` کار می‌کند، نه با یک `float` ساده. دلیلش این است که `ln(x)` برای `x < 0` در اعداد حقیقی تعریف ندارد، ولی در اعداد مختلط تعریف دارد:

```text
ln(-a) = ln(a) + iπ     (a > 0)
```

یعنی وقتی `x` منفی می‌شود، intermediate valueها ممکن است مختلط شوند.

اما خود challenge در نهایت فقط این را مقایسه می‌کند:

```python
evaluated = evaluate(expr, x).real
```

پس تنها **قسمت حقیقی** خروجی برای ما اهمیت دارد.

این یکی از کلیدهای مهم حل است: لازم نیست expression ما در تمام intermediateها کاملاً حقیقی بماند؛ کافی است **بخش حقیقی نهایی** درست باشد.

# 3. یک primitive بسیار مهم: صفر

حالا که `ln` داریم:

```text
ln(1) = 0
```

پس:

```python
def ZERO():
    return LOG("1")
```

این یعنی حتی `0` هم مستقیماً در grammar مجاز نبود، اما می‌توانیم آن را بسازیم.

---

# 4. ساختن تفریق

حالا `ln` و `exp` را داریم.

می‌خواهیم `p-q` بسازیم.

از تعریف `eml` استفاده می‌کنیم:

```text
eml(ln(p), exp(q))

= exp(ln(p)) - ln(exp(q))

= p - q
```

در نتیجه:

```text
p - q = eml(ln(p), exp(q))
```

و solver:

```python
def SUB(p, q):
    return EML(LOG(p), EXPF(q))
```

این نقطه در واقع مرز عبور از یک grammar محدود به یک زبان محاسباتی واقعی است. از اینجا به بعد تقریباً همه‌چیز را می‌توانیم از روی تفریق بسازیم.

---

# 5. ساختن `-x` و `x+y`

برای ساختن منفی یک مقدار `w`، از این متغیر استفاده می‌کنیم:

```text
-w = (1-w)-1
```

پس:

```python
def ONEMINUS(w):
    return SUB("1", w)


def NEG(w):
    return SUB(ONEMINUS(w), "1")
```

حالا اگر تفریق داریم، جمع هم راحت است:

```text
x + y = x - (-y)
```

در solver:

```python
def ADD(u, w):
    return SUB(u, NEG(w))
```

پس تا اینجا از primitive اولیه به این عملیات‌ها رسیده‌ایم:

```text
exp
ln
0
-
+
negative
```

---

# 6. ساختن ثابت‌های صحیح

Grammar فقط اجازه می‌دهد `1` را مستقیماً بنویسیم. پس مثلاً `5` را نمی‌توانیم همین‌طوری بنویسیم.

اما چون `+` داریم:

```text
5 = 1 + 1 + 1 + 1 + 1
```

solver همین کار را انجام می‌دهد:

```python
def CONST(n):
    if n == 0:
        return ZERO()
    if n > 0:
        e = "1"
        for _ in range(n - 1):
            e = ADD(e, "1")
        return e
    return NEG(CONST(-n))
```

برای عدد منفی نیز ابتدا قدر مطلق را ساخته و بعد منفی می‌کنیم.

این نکته از نظر عددی هم مهم است؛ چون challenge می‌گوید `x` می‌تواند تا حدود `10000` باشد و `a,b` در بازه‌ی `[-100,100]` هستند. بنابراین بهتر است ثابت‌ها را با عملیات‌های کوچک و کنترل‌شده بسازیم.

---

# 7. حالا نوبت ضرب است

برای ساختن `a*x`، یک identity کلاسیک داریم:

```text
x*y = exp(ln(x) + ln(y))
```

چون:

```text
ln(x) + ln(y) = ln(xy)
```

و بنابراین:

```text
exp(ln(x)+ln(y)) = xy
```

برای ضریب ثابت `a`:

```python
def MUL(a, xexpr="x"):
    s = ADD(LOG(CONST(a)), LOG(xexpr))
    return EXPF(s)
```

---

# 8. چرا این بخش از نظر overflow خیلی مهم است؟

اگر بخواهیم ضرب را به صورت خام بسازیم و یک `exp` روی مقدار بزرگی مثل `500000` انجام دهیم، خیلی سریع overflow می‌کنیم.

ولی solver این کار را نمی‌کند.

به جای:

```text
exp(a*x)
```

از:

```text
exp(ln(a) + ln(x))
```

استفاده می‌کند.

`ln(a)` و `ln(x)` نسبت به خود `a*x` خیلی کوچک‌تر هستند. بنابراین مقدار داخل `exp` معمولاً در محدوده‌ی امن باقی می‌ماند.

خود solve.py هم دقیقاً روی همین نکته تأکید می‌کند: `exp` فقط روی مقدارهای نسبتاً کوچک امن است، اما `ln` حتی برای ورودی‌های بسیار بزرگ رشد آهسته‌ای دارد. 

---

# 9. نقش اعداد مختلط در ضرب

این قسمت شاید در نگاه اول ترسناک باشد، ولی برای حل لازم نیست وارد تمام ریاضیات آن شویم.

اگر `x` منفی باشد، داریم:

```text
ln(x) = ln(|x|) + iπ
```

اگر `a` هم منفی باشد، آن یکی هم یک `iπ` اضافه می‌کند. هنگام جمع لگاریتم‌ها، این phaseها جمع می‌شوند و `exp` آنها را به علامت مناسب تبدیل می‌کند.

مثلاً اگر هر دو منفی باشند:

```text
ln(a) + ln(x)
= ln(|a|) + iπ + ln(|x|) + iπ
= ln(|a*x|) + i2π
```

و:

```text
exp(ln(|a*x|) + i2π) = |a*x|
```

که همان حاصل‌ضرب مثبت دو عدد منفی است.

اگر فقط یکی منفی باشد، یک `iπ` باقی می‌ماند و `exp(...)` یک عدد منفی می‌دهد.

یعنی عملاً بخش مختلط مثل یک **حامل علامت/phase** عمل می‌کند و در نهایت real part همان `a*x` می‌شود.

این دقیقاً یکی از دلایلی است که challenge از `np.complex128` استفاده می‌کند.

# 10. ساختن `a*x+b`

اکنون تمام primitiveهای لازم را داریم.

برای معادله‌ی:

```text
ax + b
```

ابتدا `a*x` را می‌سازیم و بعد `b` را اضافه می‌کنیم:

```python
def LINEAR(a, b):
    if a == 0:
        return CONST(b)
    m = MUL(a)
    if b == 0:
        return m
    return ADD(m, CONST(b))
```

پس برای هر round فقط کافی است ضرایب `a` و `b` را از prompt بخوانیم و `LINEAR(a,b)` را بسازیم.

# 11. چرا لازم نیست مقدارهای `x` را بدانیم؟

Challenge در هر round مقدار `x` را 100 بار به صورت تصادفی انتخاب می‌کند:

```python
x = random.uniform(-10000, 10000)
```

ولی ما expression را به صورت **symbolic** می‌سازیم.

اگر identityهایی که ساخته‌ایم درست باشند، expression ما از نظر ریاضی برای هر `x` مجاز همان `a*x+b` است.

بنابراین نیازی به حدس‌زدن یا دیدن test valueها نداریم.

ما خود function را می‌سازیم، نه جواب هر test را.

# 12. اتوماسیون ۲۰ Round

خود solver ارتباط با سرویس را هم خودکار می‌کند.

ابتدا prompt را با regex پیدا می‌کند:

```python
prompt = re.compile(rb"(-?\d+)x \+ (-?\d+) = ")
```

سپس در هر دور ضرایب را استخراج می‌کند:

```python
for i in range(20):
    chunk = io.recvuntil(prompt)
    m = prompt.search(chunk)
    a, b = int(m.group(1)), int(m.group(2))
    expr = LINEAR(a, b)
    io.sendline(expr)
```

این منطق در `solve.py` آمده است. 

پس کل حل ۲۰ مرحله‌ای کاملاً خودکار می‌شود.

# جمع‌بندی

این چالش در اصل یک تمرین **expression synthesis** بود.

ما با یک زبان تقریباً بی‌مصرف شروع کردیم:

```text
E = 1 | x | eml(E,E)
```

اما با استفاده از تعریف:

```text
eml(x,y) = exp(x) - ln(y)
```

قدم‌به‌قدم primitiveهای جدید ساختیم:

```text
exp
  ↓
ln
  ↓
subtraction
  ↓
negative
  ↓
addition
  ↓
constants
  ↓
multiplication
  ↓
a*x+b
```

و در نهایت به‌جای اینکه ۲۰ معادله را یکی‌یکی حل کنیم، یک **compiler کوچک برای grammar چالش** نوشتیم که برای هر `a` و `b` expression معتبر تولید کند.

قسمت tricky ماجرا هم فقط جبر دخیل در حل نبود؛ باید حواسمان به `numpy.complex128`، branchهای logarithm برای اعداد منفی، و جلوگیری از overflow در `exp` می‌بود.

اگر بخواهیم کل ایده را در یک جمله خلاصه کنیم:

> **به‌جای اینکه با محدودیت `eml` بجنگیم، خود `eml` را به یک زبان محاسباتی تبدیل کردیم.**
